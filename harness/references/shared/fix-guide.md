# 问题修复指南

本文档定义快速开发模式 V2 中问题修复的流程和规范。

---

## 修复流程

### 修复循环

```
代码审查 → 发现问题？
    ↓ 是              ↓ 否
问题修复          提交确认
    ↓
重新审查 ← ← ← ←
```

**循环终止条件**: 审查结果为"通过"，无待修复问题。

---

## 问题分类与优先级

| 类型 | 说明 | 优先级 |
|------|------|--------|
| 编译错误 | 代码无法编译通过 | P0 必须修复 |
| 空指针风险 | 可能导致 NPE 的代码 | P0 必须修复 |
| 逻辑错误 | 业务逻辑实现不正确 | P0 必须修复 |
| 安全漏洞 | SQL注入、XSS、敏感信息泄露 | P0 必须修复 |
| 并发问题 | 线程安全、死锁、资源泄漏 | P0 必须修复 |
| 异常处理缺失 | 外部调用无异常处理 | P1 应该修复 |
| 性能问题 | N+1 查询、循环内重复计算等 | P1 应该修复 |
| 代码规范问题 | 命名、格式等不符合规范 | P2 建议修复 |

## 修复步骤

```
分析问题 → 定位原因 → 实施修复 → 验证修复 → 重新审查
```

### 1. 分析问题

- 理解问题的影响范围
- 确认问题的优先级
- 收集相关日志、堆栈信息

### 2. 定位原因

- 找到问题代码的具体位置
- 分析问题的根本原因
- 形成明确的修复假设

### 3. 实施修复

- 按照代码规范修改代码
- 遵循最小化修改原则
- 添加必要的日志和监控

### 4. 验证修复

- 确认修复后问题已解决
- 确认未引入新问题
- 编写回归测试（如需要）

### 5. 重新审查

- 回到代码审查阶段
- 确保所有问题都已修复

## Bug 修复标准作业流程（SOP）

### 信息确认

在开始修复前，收集以下信息：

| 信息项 | 说明 |
|--------|------|
| 问题描述 | 用户或系统遇到了什么现象？ |
| 复现步骤 | 如何稳定复现该问题？ |
| 错误日志 | 完整的异常堆栈 |
| 环境信息 | 生产/预发环境、服务版本 |
| 监控数据 | 问题时间点的监控图表 |

### 本地复现

**首要目标**：在本地开发环境成功复现问题。

**复现技巧**：
- 使用相同的数据副本
- 使用相同的配置文件
- 模拟相同的依赖服务版本

### 根因分析

#### 信息分析与定位

- **日志关键字搜索**：从报错信息中提取关键字，在日志系统中全局搜索
- **时间线关联**：将问题发生时间点与发布记录、配置变更记录关联
- **Git Bisect**：使用二分查找定位引入问题的 commit

#### 问题隔离

- **最小可复现案例**：不断简化复现代码，剥离无关因素
- **二分定位法**：在代码块中间位置增加日志，判断问题在前半部分还是后半部分

### 调试技术

| 技术 | 说明 |
|------|------|
| 日志分析法 | 在关键代码处增加详细日志 |
| 小黄鸭调试法 | 将问题、代码逻辑、猜想讲述一遍 |
| 交互式调试 | 使用 IDE Debugger 逐行执行 |

## 修复后原则

### 举一反三

- 思考系统中是否存在其他类似的代码模式
- 是否可以一并修复或进行重构

### 增强可观测性

在修复问题的代码附近：
- 增加关键日志
- 增加监控埋点
- 思考：如果当初有这个日志/监控，是否能更快定位问题？

### 知识沉淀

对于有代表性的、排查过程曲折的 Bug：
- 编写简短的 RCA（根因分析）文档
- 分享到团队知识库

## 注意事项

1. **每次修复一个问题**：避免同时修改多处，便于追踪
2. **最小化修改范围**：只修改问题相关代码，不做额外重构
3. **保持代码一致性**：修复后的代码风格与项目保持一致
4. **验证修复效果**：修复后必须重新审查确认问题已解决
5. **禁止破坏性变更**：向已有父类添加抽象方法会破坏所有子类
