# 人工介入决策指南

## 触发条件

code-verify 循环超过 3 次仍未通过时，主 Agent 进入 ESCALATE 状态。

## 人工介入输出模板

```
### ⚠️ 验证循环超限，需要人工决策

**循环次数**：3次
**当前状态**：{Linter错误 / 编译错误 / 测试失败}

#### 修复历史

| 轮次 | 问题类型 | 尝试修复 | 结果 |
|------|---------|---------|------|
| 1 | {类型} | {修复摘要} | 仍失败：{原因} |
| 2 | {类型} | {修复摘要} | 仍失败：{原因} |
| 3 | {类型} | {修复摘要} | 仍失败：{原因} |

#### 当前未解决问题清单

1. {问题描述，含文件路径和行号}

#### 决策选项

1. **继续修复** — 提供补充信息或修复方向，再尝试 1 轮
2. **跳过验证** — 接受当前代码，后续手动修复
3. **回滚代码** — 撤销本次所有变更
4. **换一种实现方案** — 重新分析，换技术路线
```

## 决策建议

| 问题模式 | 建议 |
|---------|------|
| Linter 规则过于严格 | 建议调整 checkstyle.xml 或添加 suppression |
| 依赖版本冲突 | 建议手动检查 pom.xml 依赖树 |
| 外部服务不可用 | 建议跳过验证，添加 Mock 后手动测试 |
| 业务逻辑不确定 | 建议先确认需求，再重新分析 |
| 代码架构问题 | 建议换一种实现方案 |

## 阻塞性问题处理

如果遇到以下情况，立即升级为人工决策，不等 3 次循环：

1. **编译依赖缺失**：Maven 仓库中找不到依赖
2. **测试环境不可用**：H2 无法替代 PostgreSQL 的特定功能（如 pgvector）
3. **Linter 规则矛盾**：Checkstyle 和 Spotless 规则冲突
4. **代码生成陷入死循环**：coder 和 verifier 来回修复同一问题
