# 任务拆分方法论

## 原则

1. **小而完整**：每个子计划有明确的输入、输出、验证标准
2. **独立可提交**：完成后可独立提交到 git，形成可回溯历史
3. **依赖显式化**：在 exec-plan 中声明前置依赖
4. **上下文可控**：单个子计划不会导致上下文溢出

## 约束

| 约束 | 值 | 理由 |
|------|---|------|
| 变更文件数 | ≤15 | 避免单次变更范围过大 |
| 预估交互数 | ≤5 | 减少上下文膨胀 |
| exec-plan 步骤 | ≤8 | 单次可执行完毕 |
| 单步变更行数 | ≤200 | 审查友好 |

## 拆分策略

### 按功能模块拆分

最常见的拆分方式，每个功能模块作为一个子计划。

示例："开发用户管理系统"
```
P1: 用户 CRUD（Entity + Repository + Service + Controller）
P2: 角色 CRUD
P3: 权限管理
P4: 用户-角色关联
```

### 按层次拆分

复杂功能按技术层次拆分，从底层到上层。

示例："开发支付模块"
```
P1: 数据层（Entity + Repository）
P2: 核心业务层（PaymentService + 风控逻辑）
P3: 对外接口层（Controller + DTO）
P4: 集成测试
```

### 按接口拆分

跨模块功能，先定义接口再各自实现。

示例："添加审计日志"
```
P1: 审计日志接口定义 + 基础设施（Entity + Repository + Service 接口）
P2: 用户模块接入审计
P3: 订单模块接入审计
P4: 报表模块接入审计
```

### 不拆分的情况

| 类型 | 理由 |
|------|------|
| 单一 Bug 修复 | 范围小，无需拆分 |
| 单一 CRUD | 一个子计划即可 |
| 配置变更 | 通常一个文件，无需拆分 |
| 文档更新 | 非代码变更，无需拆分 |

## 依赖管理

### 声明依赖

在 exec-plan 的前置条件中声明：

```markdown
## 前置条件
- [ ] P1 用户管理已完成（UserService 可用）
- [ ] 数据库迁移脚本已执行
```

### 拓扑排序

Harness 编排层根据依赖关系确定执行顺序：

```
P1(无依赖) → P2(依赖P1) → P3(依赖P1) → P4(依赖P2,P3)
```

无依赖的子计划可并行（如 P2 和 P3），但 Harness 默认串行执行。

### 循环依赖

如果出现循环依赖（A 依赖 B，B 依赖 A），必须通过接口拆分打破：

```
A 依赖 B 的接口 → 先定义接口（子计划P0）→ A 和 B 各自实现
```

## 评估拆分质量

拆分完成后，用以下标准评估：

- [ ] 每个子计划 <15 文件
- [ ] 每个子计划可独立验证
- [ ] 依赖关系无环
- [ ] 关键路径上的子计划优先级最高
- [ ] 每个子计划完成后有明确的文档输出
