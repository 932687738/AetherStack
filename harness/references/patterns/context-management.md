# 上下文管理策略

## 核心问题

AI 在连续执行多个子计划后，上下文会不断膨胀：
- 代码细节堆积
- 验证日志累积
- 中间状态占用空间

如果不主动管理，上下文溢出会导致 AI 遗忘关键信息、输出质量下降。

## 三层上下文结构

### 始终保留（核心上下文）

| 内容 | 大小控制 | 用途 |
|------|---------|------|
| CLAUDE.md | ≤100 行 | 项目约定 |
| AGENTS.md | ≤100 行 | 模块索引 |
| 当前 exec-plan | ≤100 行 | 正在执行的计划 |

### 按需加载（工作上下文）

| 内容 | 加载时机 | 用途 |
|------|---------|------|
| ARCHITECTURE.md | 涉及架构变更 | API 列表、架构图 |
| DESIGN.md | 涉及编码规范 | 编码标准 |
| INDEX.md | 需要查找文档 | 文档定位 |
| 前置子计划 summary | 有依赖关系 | 决策参考 |

### 不加载（归档上下文）

| 内容 | 获取方式 |
|------|---------|
| archive/ 文件 | 仅在被显式引用时读取 |
| 代码变更历史 | git log |
| 验证日志 | 已归档，不主动加载 |

## 子计划间上下文切换

每个子计划完成后执行：

```
1. 生成 summary（≤50行）→ 写入 archive/
2. 更新 PLANS.md 状态
3. 推送代码
4. 提示用户压缩/清空上下文
5. 加载下一个子计划的 exec-plan
6. 加载前置 summary（如有依赖）
```

## 文档行数约束

| 文件类型 | 约束 | 理由 |
|---------|------|------|
| 始终加载（CLAUDE.md, README.md, AGENTS.md） | ≤100 行 | 每次对话都占用上下文 |
| 按需加载（ARCHITECTURE.md, DESIGN.md） | ≤300 行 | 偶尔加载，可承受稍大 |
| 索引文件（PLANS.md, INDEX.md） | ≤100 行 | 纯信息，表格即可 |
| 子计划 summary | ≤50 行 | 上下文保留时的参考 |
| exec-plan | ≤100 行 | 执行时的核心依据 |

超限处理：详见 [doc-compression.md](doc-compression.md)

## 按需读取策略

当文档超过 500 行时：

1. **先读目录**：读取文件前 30 行（标题 + 目录）
2. **定位章节**：根据目录确定需要读取的行范围
3. **按需读取**：只读取相关章节，跳过无关内容
4. **避免全文加载**：尤其不要全文加载 archive/ 文件
