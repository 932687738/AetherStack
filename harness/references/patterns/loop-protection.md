# 验证循环保护机制

## 问题

代码验证可能失败，需要修复后重新验证。如果修复不当，会陷入无限循环：

```
验证失败 → 修复 → 验证失败 → 修复 → ...
```

## 机制

### 循环计数

```
verifyLoopCount = 0  // 初始值

每次验证不通过:
  verifyLoopCount++

if verifyLoopCount ≤ MAX_LOOP (默认3):
  修复代码 → 重新执行完整三步验证
else:
  升级用户（输出问题清单 + 修复历史）
```

### MAX_LOOP 默认值：3

- 3 次足以修复大部分问题
- 超过 3 次通常意味着根本性问题（架构错误、接口不存在等）

可在 `harness.config.yaml` 中调整：

```yaml
verify:
  loop_max: 3  # 默认3，可调为5
```

## 修复策略

### 按优先级修复

| 优先级 | 类型 | 修复方式 |
|--------|------|---------|
| P0 | 编译错误 | 必须修复，否则无法继续 |
| P0 | Linter Error | 必须修复 |
| P1 | 测试失败 | 修复代码或测试 |
| P2 | Linter Warning | 可选修复 |
| P2 | 人工审查建议 | 记录但不阻塞 |

### 每次修复后完整验证

修复代码后，必须从 Step 1 开始重新走完整三步验证（Linter → 编译 → 测试），不能只验证失败的那一步。

原因：修复 A 问题可能引入 B 问题。

## 升级用户

当循环超限时，输出结构化的升级报告：

```markdown
## 验证循环超限（3次）

### 当前问题清单

#### 编译错误
1. User.java:42 - 找不到符号: method findById(Long)
2. RoleService.java:15 - 类型不匹配

#### Linter 错误
1. UserController.java:28 - 缺少 Javadoc

#### 测试失败
1. UserServiceTest.testCreate - 期望状态码200，实际500

### 修复历史

| 轮次 | 修复内容 | 结果 |
|------|---------|------|
| 1 | 添加 import 语句 | 编译通过，但 Linter 报错 |
| 2 | 添加 Javadoc | Linter 通过，但测试失败 |
| 3 | 修改测试数据 | 测试仍失败（根本原因未解决） |

### 根因分析

可能的根本原因：
1. UserService.findById() 接口在当前版本不存在（可能在 P2 中定义）
2. 建议人工确认接口可用性，或调整子计划拆分

### 建议操作

- [ ] 人工检查接口可用性
- [ ] 调整 exec-plan 步骤顺序
- [ ] 将当前子计划标记为 Blocked
```

## 特殊情况

### 自动修复可用

如果 Linter 提供自动修复命令（如 `mvn spotless:apply`、`ruff check --fix`），先执行自动修复，不计入循环次数。

```
Linter 失败 → 自动修复 → 重新 Linter
  ↓ 仍失败
  计入 verifyLoopCount
```

### 编译错误导致无法测试

如果编译失败，跳过测试步骤：

```
Linter 通过 → 编译失败 → 修复（不计入测试循环）
```

只有当编译通过后才开始测试循环。
