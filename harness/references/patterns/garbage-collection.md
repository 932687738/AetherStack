# 上下文垃圾回收

> 本文档定义 Harness Engineering 中上下文垃圾回收（GC）的策略和触发规则。

## 核心原则

**上下文是有限资源**。每个子计划完成后，残留的中间产物会持续占用上下文窗口。垃圾回收确保上下文始终为当前任务服务，不被历史数据拖入 Dumb Zone。

## 回收目标

| 目标 | 说明 | 回收时机 |
|------|------|----------|
| 设计文档 | `docs/plans/{task-key}/sp{n}-{name}.md` | 阶段6 归档后 |
| 执行计划 | `docs/plans/{task-key}/sp{n}-{name}-exec.md` | 阶段6 归档后 |
| 审查报告 | verifier 输出的验证报告 | 阶段5 完成后 |
| 修复历史 | 循环修复的详细记录 | 阶段4 验证通过后 |
| 探索中间结果 | 代码探索产生的临时笔记 | 阶段3 编码完成后 |

## 回收策略

### 一、文件级回收（阶段6 执行）

归档不是删除，而是移出工作目录：

```
docs/plans/{task-key}/  →  docs/archive/{task-key}/
```

归档后更新 INDEX.md，将文档条目标记为 `[已归档]`。

### 二、上下文级回收（阶段5/6 执行）

将详细内容压缩为摘要，保留决策和结论：

| 压缩前 | 压缩后 | 压缩比 |
|--------|--------|--------|
| 设计文档全文（~200行） | 关键决策 + 接口清单（~20行） | 10:1 |
| 验证报告（~50行） | 通过/失败 + 遗留项（~5行） | 10:1 |
| 修复历史（~30行/轮） | 根因 + 修复方案（~10行） | 3:1 |

### 三、索引级回收（阶段6 执行）

INDEX.md 中的条目按生命周期管理：

| 条目状态 | 条件 | 处理 |
|----------|------|------|
| 活跃 | 文件存在且未归档 | 正常加载 |
| 已归档 | 文件已移至 archive/ | 标记 `[已归档]`，不主动加载 |
| 过期 | 对应功能已移除 | 删除条目 |

## 触发规则

### 自动触发

| 触发条件 | 动作 |
|----------|------|
| 子计划完成（阶段6） | 执行文件级 + 上下文级回收 |
| 上下文利用率 > 40%（warning） | 提示：建议执行压缩或 context reset |
| 上下文利用率 > 60%（critical） | 强制：生成交接文档 + 提示 /clear |
| 对话轮数 > 15 轮 | 评估是否需要压缩中间产物 |

### 手动触发

用户可随时要求：
- "压缩上下文" → 生成结构化交接文档，提示 /clear
- "清理归档" → 批量处理已完成的子计划产物

## 压缩模板

子计划完成后的摘要格式（≤20行）：

```markdown
## [P1] <子计划名称> - 完成摘要

### 关键决策
- <决策1>
- <决策2>

### 接口变更
| 操作 | 接口 | 说明 |
|------|------|------|
| 新增 | POST /api/xxx | xxx |

### 依赖影响
- <对后续子计划的影响>

### 遗留项
- [ ] <如有未完成项>
```

## 不回收的内容

以下内容即使子计划完成也应保留在上下文中，直到整个需求关闭：

| 内容 | 原因 |
|------|------|
| PLANS.md | 全局状态跟踪 |
| AGENTS.md 防错规则 | 跨子计划生效 |
| 交接文档 | 下一子计划的输入 |
| harness.config.yaml | 全局配置 |
