# 技术方案模板

本文件提供技术方案文档的编写规范和模板。编写技术方案或 design.md 时参考此文档。

## 与 OpenSpec 的关系

| 技术方案章节 | OpenSpec 文件 | 说明 |
|-------------|--------------|------|
| 一. 概述 + 影响分析 | proposal.md | Why + Impact |
| 二. 业务分析（场景部分） | spec.md | What（业务需求） |
| 三~六. 系统/详细/接口/代码改造分析 | design.md | How（技术实现） |
| 实施任务 | tasks.md | 任务清单 |

## 标记说明

| 标记 | 含义 | 简单需求 | 复杂需求 |
|------|------|----------|----------|
| 【强制】 | 必填 | 必填 | 必填 |
| 【推荐】 | 建议填写 | 可跳过 | 建议填 |
| 【复杂】 | 复杂需求才需要 | 跳过 | 必填 |

### 简单/复杂需求判断标准

| 维度 | 简单需求 | 复杂需求 |
|------|----------|----------|
| 模块范围 | 单模块 | 多模块/跨系统 |
| 数据库 | 无变更或加字段 | 新建表 |
| 接口 | ≤2 个接口变更 | >2 个或新模块接口 |
| 流程 | 无新流程 | 新业务流程 |
| 架构 | 无决策 | 需要技术选型/决策 |

## 二. 业务分析

### 2.1 业务用例【复杂】

用例图描述需求范围，标识用户和系统提供的服务。

**要求：**
- 新用例用不同颜色标记
- 给出图例说明

### 2.2 业务流程【复杂】

**必须使用 Mermaid 语法**（禁止纯文本树状结构）

#### 2.2.1 活动图

描述跨角色的业务活动流程，使用 `flowchart TD`。

#### 2.2.2 流程图

描述系统内部处理流程，使用 `flowchart LR/TD`。

**要求：**
- 新流程或节点用不同颜色标记
- 节点文字使用中文

### 2.3 业务场景【强制】

详细的业务场景描述放在 OpenSpec 规范文档中：

```markdown
详见：openspec/changes/[change-id]/specs/[domain]/spec.md
```

**场景格式参考：**
```markdown
#### 场景: 场景名称

**前提**：[初始状态]

**操作**：[用户或系统执行的操作]

**预期**：
1. [预期结果1]
2. [预期结果2]
```

## 三. 系统设计

### 3.1 业务实体状态图【复杂】

状态机用于对模型元素的动态行为进行建模。

**要求：**
- 新状态节点用不同颜色标记

### 3.2 领域模型图【复杂】

领域模型包含上下文边界、领域实体、聚合、值对象、领域能力、领域事件、仓储等。

**最低要求：**
- 上下文边界
- 领域实体
- 聚合
- 领域事件（消息体）
- 关系的结构明细

**要求：**
- 新模型用不同颜色标记
- 如果没有模型变更，可省略此部分

> 领域模型参考 `references/domain-models.md`

### 3.3 数据模型图【强制】

描述数据模型的 E-R 关系。无变更时注明"无数据模型变更"。

**要求：**
- 表达实体之间的关系（1:1、1:N、N:N）
- 标注关键实体及其关联
- DDL/DML 详细定义放到"四. 详细设计"

> 数据模型规范参考 `references/architecture.md` 的"数据模型层架构模式"部分

**要求：**
- 新调用关系用不同颜色标记

### 5.2 接口详细设计【强制】

新增接口必须详细定义。

**要求**：
- 契约必须绑定到具体接口/方法/DTO，并与代码改造分析对齐

#### POST /api/path/to/endpoint

**功能**：[接口功能描述]

**请求参数**：
```json
{
  "field1": "string, 必填, 字段说明",
  "field2": 123,       // Long, 选填, 字段说明
  "nested": {          // Object, 嵌套对象示例
    "subField": "value"
  },
  "list": [            // List, 数组示例
    { "item": "value" }
  ]
}
```

**响应格式**：
```json
{
  "code": 0,           // Integer, 状态码
  "message": "success", // String, 提示信息
  "data": {
    "id": 123,         // Long, 记录ID
    "items": []        // List, 数据列表
  }
}
```

**错误码**：
- `ERR_001`：错误描述
- `ERR_002`：错误描述

## 六. 代码改造分析【强制】

> 要求：
> 1) 必须覆盖所有关键路径/关键分支（入口 → 核心校验 → 数据落点）
> 2) 每条包含"代码位置 / 现状代码 / 风险点 / 改造要点"
> 3) 现状代码和改造要点必须给出具体代码片段（不能只是描述）
> 4) 必须覆盖关键分支：正常流程、参数异常、并发冲突、数据不一致、回滚
> 5) 顺序建议：入口链路 → 核心校验/分支 → 数据落点/后置处理
> 6) 每条之间空一行，增强可读性

**现状代码**：
